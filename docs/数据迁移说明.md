# 数据迁移说明（v1 / v2 → v3）

## 一、版本与存储键

- 当前数据结构版本：`SCHEMA_VERSION = 3`（`src/core.js`）。
- 存储键：
  - 病历列表：`dabingli.records.v1`
  - 当前草稿指针：`dabingli.current.v1`，值为 `{ id, at }`，只表示“上次打开哪一份”
  - 每份病历草稿：`dabingli.draft.v1.<id>`
  - 设置：`dabingli.settings.v1`
- 列表键和设置键不改名，避免升级后“找不到旧病历”。
- v3 起草稿按病历分开存储，解决多个标签页编辑不同病历时互相覆盖 `current` 的问题。

## 二、迁移入口

所有入口都走 `RECORD_CORE.normalizeRecord(raw, emptyRecord, validDeptKeys)`：

1. 启动时读取当前草稿：`loadCurrent()`。
2. 打开病历列表：`loadList()`。
3. 导入备份：`parseImport()` 逐条调用。
4. 撤销快照：`undoLast()` 重新规范化快照。

`normalizeRecord` 先补结构、再校验、最后迁移，缺字段的旧存档不会被拒绝。

### 浏览器 Web UI 的 IndexedDB 入口

- `@dabingli/storage` 首次初始化时只读扫描上述旧 localStorage 键；只有 IndexedDB
  为空才迁移。
- 迁移统一调用 `normalizeRecord`，成功后把状态写入 `meta.browserLegacyMigration`。
- 旧 localStorage 键不修改、不删除，保留为回滚来源；任一旧记录损坏时不写入新库。
- 替换导入先在同一个 IndexedDB 事务中保存恢复副本，再替换记录、草稿和当前指针。

## 三、字段映射与处理

| 旧数据 | v3 处理 |
|---|---|
| `schemaVersion: 1` 或 `2` | 记录 `meta.migratedFrom`，追加迁移说明；结构补到 v3。 |
| `basic.marital` 与 `marriage.status` 都有值且相同 | 以 `basic.marital` 为准，清空 `marriage.status`，追加“两处一致，已统一到基本情况”。 |
| 两处都有值但不同 | 两个原值都保留：`meta.conflicts.marriage = { basicValue, marriageValue, resolved:false, chosen:'' }`；界面提示选择，生成器不静默取舍。 |
| 只有 `marriage.status` | 迁移到 `basic.marital`，清空 `marriage.status`。 |
| 只有 `basic.marital` | 保持不变。 |
| 旧摘要文字 | 保留原文；`documentMeta.summary.origin = 'legacy'`，不判为已核对。 |
| 旧首次病程录 S / O 体检 / O 辅助检查 / 诊断依据文字 | 逐段保留；对应段 `origin = 'legacy'`。 |
| 旧出院记录入院情况文字 | 保留；`documentMeta.discharge.admitCondition.origin = 'legacy'`。 |
| 旧出院诊断列表 | 保留；`documentMeta.discharge.diagnoses.origin = 'legacy'`，`confirmed = false`。 |
| 旧字段有内容但没有来源记录 | `meta.fieldStates[path].source = 'legacy'`，`reviewed = false`。 |
| 旧字段没有内容 | 不写 `fieldStates`，保持空白。 |
| 旧模板标记 `__templateKey` | 原样保留，继续用于阻止混用不同模板。 |
| 科室中文名 / 简称 / 英文大小写 | 通过 `normalizeDeptKey()` 归一；不认识的科室回退到 `general`。 |
| 旧版 `dabingli.current.v1` 存的是整份病历 | 首次读取时迁移到 `dabingli.draft.v1.<id>`，并把 `current` 改写为指针；返回 `migrated:true`。 |
| `basic.age` 为数字 | 转成字符串。 |
| `chiefComplaintDuration` 为数字 | 转成字符串。 |
| 诊断列表含空串 / 首尾空白 | 去空、去空白。 |
| `auxiliary.items` 为空 | 补一行 `{ name:'', result:'', date:'', hospital:'', no:'' }`，保证界面可输入。 |

## 四、明确不改写的内容

### 完善入院记录模板（第 3 批）的兼容增量

- 保持 `SCHEMA_VERSION = 3`：只增加检查条目的可选 `category`（`lab` / `special` / `pathology`），不改存储键、Android 包名或 WebView origin；Android 原生暂存/校验/事务/回滚协议不变。
- `pmh` 整段字符串映射到 `pmh.diseaseDetail`，完整原文另存 `meta.legacyUnmapped.pmh`，不猜测拆分疾病、手术、过敏等语义；已有对象字段不搬动、不覆盖。
- `auxiliary` 旧数组变为 `{items: 原条目}`；旧文本或列表中的字符串变为可见且可编辑的“旧辅助检查”条目，旧整段文本另存 `meta.legacyUnmapped.auxiliary`。原条目的 `name/result/date/hospital/no` 和未知属性均保留。
- 无 `category` 时仅在导出/预览时按项目名分类，不修改原检查列表及排序；病理归特殊检查，无法判断归实验室。用户可在两端表单明确指定分类，显式分类优先。
- 修复嵌套路径写入对数组的处理：网页逐项编辑 `auxiliary.items.<序号>` 时保留原数组、同条检查的其他字段和其他条目，避免误变成数字键对象。
- `ros` 不再参与表单、导航、预览、TXT、完整性要求或 AI 识别/整理；normalize 不再把旧布尔 `true` 转换成三态对象，整个旧对象含扩展属性原样存储和备份。取消显示不是删除旧数据，JSON 导入/导出继续携带它。
- 出生日期、籍贯、工作单位、通讯地址、电话号码仍保留并可编辑，只不进入医院入院记录的固定基本项目；摘要、SOAP、出院记录原文继续保留。
- 回归样本置于 `tests/fixtures/template-alignment/`，不修改冻结的 `tests/fixtures/legacy/` 六份基线。新增测试覆盖 v2 合并结构 → v3、JSON 备份往返、迁移幂等、IndexedDB 重开及旧 localStorage 不变。

- 不清空任何旧文字，包括来源不明的手写摘要、SOAP、出院记录。
- 不因为文字恰好等于模板默认值就认定它来自模板。
- 不把旧内容默认标成“已核对”。
- 不把旧出院诊断自动复制到 `discharge.diagnoses`；出院诊断为空时保持待填。
- 不根据旧文字反推生命体征、检查数值或诊断。

## 五、冲突处理

### 婚姻状态

- 一致：直接合并，无冲突记录。
- 不一致：保留 `basicValue` 与 `marriageValue`，`resolved:false`。
- 用户选择后调用 `resolveMarriage(record, value)`，写入 `basic.marital`、清空 `marriage.status`、记录 `chosen` 与 `resolved:true`。
- 未解决前生成器只读 `basic.marital`，界面提示两处不一致。

### 生成段落

- 旧文字没有来源：`legacy`，可查看、可比较、可手动确认，不会被自动覆盖。
- 旧文字有来源但资料已变化：按 `origin` 与指纹判断为 `manual-stale` 或 `reviewed-stale`。
- 旧文字没有 `documentMeta`：不补造生成指纹，避免把“旧文字”误认为“当前资料的生成结果”。

## 六、导入与备份

- `buildExport(list, isoNow, opts)`：
  - 默认导出病历列表。
  - `opts.includeDraft === true` 时把当前草稿并入，导出文件带 `includesDraft: true`。
  - 原始笔记默认不导出；`opts.includeNotes === true` 时保留每条 `rawNotes` 并写 `includesNotes: true`。
  - 同一 ID 的列表记录与草稿只保留一份（按 `upsertRecord` 规则更新）。
- `parseImport(rawText, emptyRecord, validDeptKeys)`：
  - 支持 `{ records: [...] }` 包装和单份病历。
  - 每条都走 `normalizeRecord`。
  - 只有 `includesNotes: true` 且该条数据确实含 `rawNotes` 键时，才把笔记视为备份内容。
  - `schemaVersion > 3` 明确拒绝，不修改当前数据。
- `mergeImport(list, imported)`：
  - 同 ID 比较 `updatedAt` 字符串，较新者覆盖，否则跳过。
  - 覆盖时若备份未包含该条原始笔记，保留本机同 ID 记录的 `rawNotes`。
  - 不同 ID 直接追加。
- `replaceImport(imported, existingList)`：整体替换；同 ID 且备份未包含原始笔记时保留本机笔记。调用前先写恢复副本，恢复副本写入失败则不继续替换。

## 七、异常与回滚

- `loadList()` / `loadCurrent()` 捕获 `localStorage` 访问异常和 JSON 解析异常，返回 `{ ok:false, corrupt:true, raw }`，原始字符串保留供导出。
- 当前草稿损坏时暂停自动保存，不把空白病历写回损坏槽。
- 某份病历草稿损坏时只影响该 id，其他病历的草稿仍可正常读取。
- 写入失败时保留内存内容，界面明确提示“尚未写入本机”。
- 撤销快照只在本机内存，刷新后失效；它不是异地备份。
- 迁移后的存档再次保存时写 `schemaVersion: 3`；旧备份仍可导入。

## 八、兼容性结论

- v1 / v2 存档可读、可迁移、可继续编辑。
- v3 存档在旧版本应用中会被“来自更新版本”规则拒绝，这是预期行为。
- 旧备份导入新版后，文字保留、来源不明可见、冲突可见；不会因为迁移产生新的患者事实。
